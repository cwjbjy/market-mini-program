## Context

"家庭厨房"小程序首页现有：hero 标题区、toolbar（搜索框 + 新建菜谱 + 分类管理）、分类侧栏 + 菜谱列表、底部购物车浮条与 `t-popup` 购物车弹层。后端 `recentWithItems` 返回最近 **50 单**（`ORDER BY created_at DESC LIMIT 50`，`deleted_at IS NULL`，无日期过滤），订单页 `pages/order/order.js` 通过 `api.getOrders()` 消费它；**首页 `index.js` 当前只加载 categories，不加载 orders**。

转盘是纯消费侧功能：复用现有菜谱列表与订单历史，不新增写入路径，不改现有 CRUD 契约。

## Goals / Non-Goals

**Goals:**

- 在首页提供"没想法时帮我定"的随机选菜入口，与搜索互补。
- 转盘永远清晰可读（固定 6 格），且通过"换一批"覆盖整个候选池。
- 优先推荐"好久不见/从未吃过"的菜，近 7 天吃过的降权；池子不足时按"最久没吃"优先保底凑满 6 道。
- 尽量纯前端实现，复用现有弹层与图标组件。

**Non-Goals:**

- 不做用户体系/多人投票/社交分享。
- 不做转盘以外的游戏化（成就、图鉴、打卡）。
- 不改菜谱/订单的数据模型与对外 JSON 契约。
- 不追求密码学级随机；`Math.random` 足够。

## Decisions

### D1：入口放 toolbar 搜索旁（方案 B），而非 hero / FAB

搜索框后新增一个纯图标 🎲 按钮。**理由**：转盘与搜索是互补的"决策入口"（有想法→搜索，没想法→转盘），语义成对、心智一致；图标按钮不占文字宽度，小屏可容纳。**否决**：hero 方案会牺牲品牌 banner 视觉；FAB 与底部购物车浮条抢位置且遮挡列表。

### D2：弹窗转盘，复用 `t-popup`

沿用购物车的底部/中央弹层模式，不 `navigateTo` 独立页。**理由**：交互一致、无页面跳转开销、关闭即回首页。**否决**：独立全屏页仪式感更强但增加导航层级与分包页面，对一个轻量趣味功能偏重。

### D3：固定 6 格，而非"候选全上"或动态格数

**理由**：6 格 = 60°/格，能放下 7 字中文菜名（如"百香果番茄牛肉"）；格数固定保证视觉稳定与可读性。候选池可能远大于 6，转盘只承载"随机精选切片"，靠"换一批"覆盖全池。**否决**：候选全上（15+ 格）每格 ≤24° 菜名不可读，等于把浏览难题搬进转盘；动态格数破坏视觉一致性。

### D4：抽样算法 = 按"距上次吃天数"排序取前 6

```
全部菜谱按 lastEaten 升序排（从未吃过 = null = 最久 = 排最前）
  新鲜池 = 近7天没吃过（含从未吃过）
  最近池 = 近7天吃过（已按最久→最近排好）

if 新鲜池.length >= 6:  转盘 = randomSample(新鲜池, 6)
else:                   转盘 = 新鲜池全部 + 最近池.slice(0, 6 - 新鲜池.length)
```

**理由**：单一排序键统一表达"鼓励尝新 + 好久不见优先 + 保底放回最久没吃"三个意图，无需额外分支；从未吃过的菜天然排最前。保底时"昨天刚吃的"最后才放回，守住排除本意。**否决**：硬排除后再随机补位——会把昨天刚吃的随机转出来，违背初衷。

### D5："最近"窗口 = 近 7 天

以订单 `createdAt`（UTC）为准，`now - lastEaten <= 7天` 视为最近吃过。**理由**：7 天覆盖"上周吃过的可以回归、这几天吃腻的别再来"的家庭节奏。**否决**：上一单（排除力度太弱）、3 天（偏短，池子偏大但排除不足）。

### D6：数据源——前端计算（默认），后端统计接口为升级路径

- **默认（纯前端）**：首页菜单渲染后在后台调用现有 `api.getOrders()`（LIMIT 50），从 `items[].recipeId` 和 `createdAt` 聚合每道菜 `lastEaten = max(createdAt)`，再按 D4 抽样。首页实例缓存订单统计与候选名单，在首次准备完成后启用骰子入口。关闭重开复用名单，点「换一批」时用当前菜谱和缓存的订单统计重新计算。菜单刷新时更新候选菜的名称和图片，名单中有菜被删除或候选数量失效时重新准备。
- **升级路径（后端）**：若高频下单导致 50 单不足覆盖 7 天，新增只读接口 `GET /api/recipes/last-eaten` 返回 `{recipeId: lastEaten}`（`order_items JOIN orders` 按 `recipe_id` 取 `MAX(created_at)`，`deleted_at IS NULL`），前端改调它。**理由**：精确覆盖全历史、无 LIMIT 隐患、单次轻量请求。

**否决的备选：在 recipes 上存 `last_eaten_at`（反规范化）**。曾考虑给菜谱加一个"最后食用时间"列，下单时更新、读时直取，免去 JOIN。否决理由：

- `last_eaten_at` 是 **MAX 聚合**，会因隐藏/删除订单而**倒退**（最近一单被隐藏后，真正的最后食用时间退回更早一单）。存储字段若不重算就会变脏，于是每次隐藏/删除订单都得回头重算受影响菜谱——读端省下的便利加倍还到写端。
- 对照 `recipes.order_count`：它是**单调只增**计数器，隐藏订单不影响它，所以冗余几乎零成本；`last_eaten_at` 可增可减，冗余是持续的一致性负担。两者不可类比。
- 本项目数据规模小（几十道菜、几百单），读时 `GROUP BY` 聚合毫秒级、几乎零成本，反规范化收益≈0 但维护成本照付。
- 存储字段若不重算会违背 spec"隐藏订单不计入吃过"；订单是唯一真相，读时计算可自动免费保证隐藏/删除语义正确。

结论："最后食用时间"是订单的派生事实，留在订单里读时算出，不在菜谱上养会过期的副本。

详见 Risks 中的 LIMIT 50 边界。

### D7：转盘渲染——canvas 2d 扇区 + 旋转动画

用 Canvas 2D 绘制 6 个扇区及菜名，按经过时间逐帧绘制旋转角度。每帧恢复画布坐标后，再在十二点方向绘制固定指针，让指针和盘面显示在同一层。旋转停止时按最终角度反算中奖格。Canvas 初始化失败时，用名单保留随机选菜操作。

### D8 抽中后确认加购

转盘停止后保留盘面，显示抽中的菜名，同时提供「再转一次」和「加入购物车」。「再转一次」沿用当前候选菜，从盘面的停止角度继续旋转，停下后更新结果。转动期间禁用加购。确认后复用 `cart.adjustQuantity(recipeId, +1)` 加一份，关闭弹窗，提示「已把『X』加入购物车」并更新首页购物车。关闭弹窗或换一批会清除结果。Canvas 降级时可「再选一次」，小菜单的推荐卡片也使用「加入购物车」按钮。存在待确认订单（`cartPending`）时禁用旋转和加购。

## Risks / Trade-offs

- **[LIMIT 50 在高频下单时不足覆盖 7 天]** → 某些"6 天前吃过"的菜未出现在最近 50 单里，被误判为新鲜。家庭场景概率极低；若出现，按 D6 升级路径切后端统计接口。
- **[隐藏订单不计入"吃过"]** → `recentWithItems` 过滤 `deleted_at IS NULL`，被隐藏订单里的菜不算吃过。视为可接受（隐藏即意图遗忘），文档注明。
- **[首页新增一次 orders 请求]** → 菜单渲染后再请求，失败时按全池抽样，打开转盘时显示提示。
- **[保底模式下新鲜菜常驻]** → 新鲜池 < 6 时换一批只轮换补位格，新鲜菜固定。这是有意行为（让好久不见的菜稳定曝光），非 bug。
- **[极小菜单转盘滑稽]** → 总菜谱 < 6 时退化为"今天就吃它"卡片；空菜单提示先建菜谱。
- **[canvas 兼容性/性能]** → 低端机旋转动画可能掉帧；限制动画时长与帧率，必要时降级 CSS 方案。

## Migration Plan

纯新增功能，无数据迁移。部署即生效；回滚 = 移除 toolbar 🎲 按钮与弹窗组件（前端单点），后端若加了统计接口可保留（只读、无副作用）或一并移除。建议用首页一个开关常量控制入口显隐，便于灰度/快速回滚。

## Open Questions

- **动画手感**：旋转时长、缓动曲线、是否配音/振动反馈，实现时调。
- **保底放回的并列排序**：两道菜 lastEaten 完全相同时的次序（可用 orderCount 或 id 兜底），实现时定。
- **数据源最终选型**：默认前端（D6），是否直接上后端接口取决于对精确度的要求。
